# 中断、时序与 CPU 开销核查

> 历史过程记录。当前编译烧录与控制行为以[文档索引](../README.md)和[运行时控制说明](../runtime_control.md)为准。

> 这是修改前的历史核查。当前已按用户确认实施 OLED、UART DMA/恢复、时间基准和 Mahony 优化，现状与验证见 [实时性优化记录](realtime_optimization.md)。其余建议仍需根据实板计时逐步验证。

本次是源码、编译配置及现有 Debug 目标文件的静态核查，未修改固件代码，未连接实板进行时间测量。下文的总线时间和滤波时间是计算值；中断执行时间、实际 CPU 占用、溢出发生频率和控制抖动均需要实测。报文互通/算法测试通过不能替代实时性测试。

## 当前实际运行结构

按现有配置，系统使用 STM32F405，时钟配置为 168 MHz，硬浮点参数为 `fpv4-sp-d16`。Debug 为 `-O0`，Release 为 `-Os`。

- `RDK_UART_CONTROL_ENABLE=1`：RDK 接管电机；原方形轨迹/遥控/语音驱动分支不执行。
- UART5 的 ELRS 接收仍启用，语音 I2C 轮询/重试仍执行，灯带仍以 5 ms 间隔更新。
- 电机编码器使用硬件编码器定时器，不是每个编码器脉冲都进入中断。
- TIM13 每 20 ms 提交四轮目标、更新轮速/PID/PWM、计算里程计，并驱动蜂鸣器节拍。
- SysTick 每 1 ms 更新 HAL 时间并检查命令超时。
- IMU 采样/Mahony、RDK 反馈启动、I2C 外设、显示、FRAM 保存均在串行主循环执行。
- RDK 串口收发为逐字节 IT；接收 ISR 内完成流式解析、CRC 和目标换算。ELRS 也是逐字节 IT，ISR 内进行 CRC、解包和遥控状态计算。

| 中断 | 当前抢占优先级 | 实际工作 |
|---|---:|---|
| USART3 | 0 | RDK RX 解析 + TX 逐字节发送 |
| UART5 | 0 | ELRS 接收/解包/状态计算 |
| USART1 | 0 | 收字节、蜂鸣器停止、续接接收 |
| DMA2_Stream2 | 0 | 灯带 DMA 半传输/完成服务 |
| EXTI15_10 | 0 | LIS3_DRDY，应用回调忽略该引脚 |
| CAN1_RX0 | 0 | 配置了 NVIC；未发现应用启用 CAN Start/通知，不能据此认定有中断流量 |
| TIM8_UP_TIM13 | 1 | 电机闭环、里程计、蜂鸣器 |
| EXTI2、EXTI9_5 | 3 | 按键/旋钮；IMU_INT 当前不用于采样调度 |
| UART4、DMA1_Stream4 | 3 | VOFA DMA 通道，当前 VOFA 开关为 0 |
| SysTick | 15 | HAL 时间、RDK 命令超时 |

分组为 `NVIC_PRIORITYGROUP_4`，数字小表示更高优先级。同抢占优先级的中断不能相互抢占，子优先级不能解决这个问题。依据 [Arm Cortex-M4 用户指南](https://documentation-service.arm.com/static/5f2ac4ab60a93e65927bbdbf)。DMA 硬件的仲裁优先级与 DMA 的 NVIC 优先级是两回事。

## 优先解决的问题

### 1. OLED 全屏清除确定会超过姿态的 50 ms 断采样门限

位置：`Core/Src/OLED.c:174`、`Core/Src/Menu.c:123`、`Core/Src/Menu.c:321`。

`OLED_Clear()` 清理 8×128 字节，每字节各调用一次阻塞 I2C 发送；每次还要发送从地址和控制字节。I2C 配置为 400 kHz，仅理想总线时间约为：

```text
1024 × (从地址1字节 + 控制1字节 + 数据1字节) × 9 / 400000
+ 8页 × 3条定位命令 × 3字节 × 9 / 400000
= 70.74 ms
```

该估算未计起停条件和软件开销。开屏/关闭显示菜单会走到这条运行期路径，不只是启动时调用。主循环超过 50 ms 没有采到新陀螺仪，当前滤波会重新对准，姿态有效位清除，并可能重新建立相对 yaw 零点。

这是已经可以从代码和总线速率确认的时序冲突。I2C 阻塞通常仍允许电机/串口中断运行，因此直接受影响的是 IMU 采样、姿态连续性和反馈周期，不能说此时所有中断都停了。

优化：统一使用行/块缓冲发送；反显也先生成一整行再发。进一步将刷新拆成有时间预算的小块，或使用统一 I2C 调度的 DMA/IT。每页 128 字节批量发送仍约 3 ms，整屏批量刷新仍会超过一次 10 ms IMU 周期，不能只把逐字节发送换成整屏批量就认为实时性已解决。

### 2. 状态页 20 ms 重绘预算连清空行都不够

位置：`Core/Src/Menu.c:10`、`Core/Src/Menu.c:432`。

状态页每次清空并重写第 1～7 行。按 400 kHz 算，7 次 `OLED_ClearLine()` 加定位命令就约 21.89 ms，还没发送任何新文字。因而当前状态页无法真正实现每 20 ms 完成一次刷新；打开状态页后会持续占用主循环时间。

`OLED_ShowStringInverted()` 又按字符、逐像素字节发送，进一步增加交互页面延迟。

优化：将显示刷新降为 5～10 Hz，只刷新变化的区域；用空格补齐整行代替“先清空再重写”；异步队列/分片每次限定工作量。降低刷新率减少平均负担，分片/异步才控制单次阻塞。

### 3. UART5/USART1 错误后可能停止接收，USART1 另有启动窗口

位置：`Core/Src/main.c:1069`、`Core/Src/ELRS.c:92`、`Core/Src/main.c:1036`。

当前全局 `HAL_UART_ErrorCallback()` 只转发到 RDK 模块，RDK 对非 USART3 句柄直接返回。所用 HAL 在 ORE 等阻塞接收错误后会终止接收；UART5、USART1 没有对应清错/重启路径。一次错误后可能表现为“接收中断再也不进”。ELRS 的 `HAL_UART_Receive_IT()` 返回值也未检查。

USART1 在外设初始化完成前已启动接收。若此时收到数据，回调在 `g_peripherals_initialized==0` 时直接返回，没有续接下一字节，初始化结束后也没有补启动。

优化：全局回调按 UART 分发；为 ELRS/USART1 提供错误恢复、解析状态重置与重启失败计数。接收启动放在可处理数据之后，或在未就绪时丢弃数据但始终续接接收。ELRS 丢链/解析失败的控制安全策略与恢复逻辑一并验证。

### 4. 最高优先级放置了大量串口解析与灯带服务

位置：`Core/Src/usart.c:227`、`:254`、`:281`，`Core/Src/dma.c:51`，`Core/Src/rdk_uart.c:346`，`Core/Src/ELRS.c:243`。

UART5=420000、8N1，连续字节间隔约 23.81 us；USART3=115200、8N1，约 86.81 us。UART5、USART3、USART1 与灯带 DMA 都是优先级 0，无法相互抢占。

RDK 在收到最后一字节时会计算整帧 CRC、移动缓冲区、校验 4 个 float、执行 4 次 `lroundf()` 并提交命令；ELRS 会做 CRC、16 通道解包、除法及开关状态计算。这些路径若延迟其他接收口读取 DR，就可能触发 ORE。是否实际超过字节服务期限需要 DWT/GPIO 测量，当前不能宣称已经发生丢字节。硬件 ORE 条件见 [ST RM0090](https://www.st.com/resource/zh/reference_manual/DM00031020.pdf)。

优化：UART5 和 RDK RX 采用循环 DMA 配合 IDLE/HT/TC 管理写指针；ISR 只保存位置/时间、设置工作标志。CRC、解包和浮点转换交给有时间预算的高优先级任务。RDK TX 改 DMA，减少逐字节 TXE 服务。灯带 IRQ 下调，测清最长关键 ISR 后统一分配优先级。

注意：主循环仍阻塞 70 ms 时，只换 DMA 仍可能令接收缓冲区覆盖。必须同时限制任务阻塞时间、选择容量并检测溢出。延后解析时保留接收时间，不能把积压的旧命令在“解析时刻”当作刚收到而刷新运动超时。

### 5. 主循环外围任务会拖延关键采样，故障情况下更明显

位置：`Core/Src/main.c:845`、`:931`；`Core/Src/IMU.c:83`；`Core/Src/INA219.c`；`Core/Src/Flash.c`。

- RDK 模式虽然不执行语音驱动，语音 I2C 轮询/重试仍执行。
- IMU SPI 阻塞调用超时参数为 100 ms。
- INA219 单次寄存器访问超时参数为 20 ms，电压读取与电流读取串行；电流读取还会先写校准寄存器。
- FRAM 写入超时参数为 100 ms；仅有参数变化时实际保存，不是每秒都写一次。
- OLED 每次发送的状态未检查，故障后可能继续大量重试。

这些是超时设置与故障路径，不是健康通信的固定耗时。设备正常 NACK 常会迅速返回，也不能把 3 次探测一律当作 30 ms。当前 HAL 的某些 BUSY 等待使用内部独立超时，所以单个 API 参数也不一定等于完整应用链路的上限。

优化：按控制模式启用外围任务；故障后退避并限制一次调度中的重试量；较短且实测可满足的超时；SPI/I2C 异步化或有预算的小事务。IMU 可从连续寄存器突发读出 gyro+accel，减少事务，并利用 DRDY 或 FIFO 保存采样，硬件端需先配置中断路由，单有 GPIO EXTI 不会自动完成。

## 控制响应与算法开销

### 6. 轮速低通本身引入约百毫秒的响应过程

位置：`Core/Src/Motor.c:6`、`:330`。

当前公式为 `filtered += 0.35 * (raw-filtered)`，每 20 ms 更新一次。忽略整数舍入，等效时间常数约 46.43 ms，阶跃到达 90% 约 106.90 ms。这是滤波器动态，不能归因于 CPU 占用。

命令四轮目标本来就在 20 ms 控制节拍提交，另有 0～20 ms 的节拍等待；编码器计数窗口和反馈发送还会带来信号年龄。

优化：根据编码器噪声/闭环带宽调整滤波强度，必要时使用测速估计器。若控制周期提高到 5～10 ms，必须同步处理每周期 Ki/Kd、低通系数和低速编码器量化问题，不能只修改定时器 ARR。

### 7. 20 ms 控制中断又用 HAL 毫秒值判定 20 ms，可能跳过测速

位置：`Core/Src/Motor.c:315`。

`Motor_UpdateEncoderSpeed()` 在 `dt_ms<20` 时直接返回，但外层 PID 仍执行。SysTick 优先级 15，电机中断优先级 1；时钟相位或调度抖动可能使某次读取差值为 19 ms，从而本次不更新测速、下次约 39/40 ms 后才更新。此时可能出现“PID 跑了，但反馈不是这个周期产生的”。具体发生率需要记录。

优化：控制中断每周期采集编码器，使用独立高分辨率计时或硬件周期计数计算实际 dt；检测迟到/漏周期。里程计当前速度计算固定除以 0.020，若发生真正漏周期也会偏差，应与同一采样快照/时间基准一致。

### 8. Mahony 不是目前最有证据的首要瓶颈，但通信侧重复做了双精度计算

Mahony 主路径使用 float，约 100 Hz，代码执行量有界。STM32F405 支持单精度 FPU，当前工程也启用了硬浮点；不能仅凭有 sinf/cosf 就判断 CPU 不够。

实际 Debug 目标文件 `rdk_uart.c.obj` 的未解析符号中确认有 `__aeabi_dmul`、`__aeabi_dadd`、`__aeabi_ddiv`、`__aeabi_f2d` 和 `sqrt`，来自四元数校验/归一化；这部分是双精度软件辅助调用。滤波本身归一化一次，`RDK_UART_UpdateOrientation()` 再校验/归一化，打包又校验/归一化，存在重复工作。

优化：对外部输入保留数值检查；可信内部路径合并重复归一化。先限制四元数分量范围，再使用 float/sqrtf，避免直接替换后失去溢出保护。里程计的 sinf/cosf 在 50 Hz 电机 ISR 内，可把带时间戳的编码器快照交给后台完成积分。短 ISR 先采样/提交/PID/PWM。

Debug 的 `-O0` 也会放大开销，性能比较应固定为实际部署配置并保留同等校验。不要用 `-ffast-math` 粗暴提速，它可能改变 NaN/Inf 检查语义，影响串口异常数值拒绝。

### 9. 灯带 200 Hz 可降频，硬件 PWM 频率不是 ISR 频率

20 颗 LED、每颗 24 bit 加 300 个复位槽，共 780 个 800 kHz PWM 槽，约 0.975 ms/次，由 DMA 输出。不能据此说 CPU 每秒进入 80 万次灯带中断。

当前每 5 ms 重新编码/发送一次，约 200 Hz。所用 HAL 配置了半传输回调，可能还有无业务用途的半传输中断。可降至 20～50 Hz、禁用不需要的 HT 事件、降低灯带 NVIC 优先级。DMA 正常输出阶段不会按每个灯珠 bit 执行算法。

## 中断健壮性与共享状态

### 10. 临界区、共享快照和时间基准需要整理

- RDK 的四轮目标提交和轮速快照使用了保存/恢复 PRIMASK 的短临界区，这是正确的同步方向。
- Peripheral/Menu 多处直接 `__disable_irq()`/`__enable_irq()`，未保存原状态。当前常见调用路径多为主循环，尚不能据此断言会破坏 RDK 临界区；但后续嵌套调用可能提前打开中断，应统一保存/恢复进入时的 PRIMASK。需要测最长关中断时间。
- `Odom_GetState()` 是多字段直接复制，`Odom_Reset()` 与 ISR 更新也未同步；主循环可能读到跨周期数据。建议双缓冲/序列计数或短快照临界区。不要把长计算整个包进关中断。
- `RDK_UART_Process(now_ms)` 先由调用者取时间，随后才在临界区读取编码器采样时间。若中间被新一周期采样抢占，采样时间可能比传入的 now_ms 新，unsigned 年龄计算会回绕，令本次有效轮速错误标为无效。建议先取得快照，再取用于年龄判断的当前时间，或统一快照时间基准。该逻辑窗口也需要修正。
- 当前 SysTick 优先级最低，1 ms 回调不是硬件保证的最大 1 ms 响应时间。高优先级 ISR 或全局屏蔽若长时间占用，会延迟 HAL 时间与软件停车。需要较强时间保证时，可使用独立硬件定时器/驱动关断链路；独立看门狗用于处理系统整体失活。

### 11. 故障死循环没有主动关 PWM，软件超时不能覆盖故障中断

位置：`HardFault_Handler()`、`Error_Handler()`。

故障处理目前只死循环，Error_Handler 还关闭全部中断。PWM 是硬件持续输出，CPU 故障时可能保持最后的输出；SysTick 软件超时无法在这些状态下执行。当前没有启用 IWDG/WWDG。

优化：故障路径先用最短、无需等待的硬件动作关闭 PWM/驱动使能，再记录必要寄存器并复位；配置独立看门狗，喂狗条件与关键任务健康状态绑定。具体关断机制应按驱动硬件确认。

此外链接脚本仅预留最小 1 KB 栈空间，这不是“已经测得栈足够”也不是硬上限。嵌套 ISR、FPU 上下文和 snprintf 需结合栈水位测量，不能从 RAM 静态占用小推断没有栈风险。

## 实测方法与验收建议

当前无限主循环没有睡眠/空闲记账，CPU 一直执行轮询也可能显示接近 100% 活跃。应区分有用计算、HAL 忙等、ISR 时间和空转，而非直接给某个算法归责。

建议添加独立的性能统计模块，计时用 DWT CYCCNT 或高分辨率通用定时器，输出走单独诊断口并低频汇总，不能把 printf 放入控制 ISR 或 RDK 协议流。

| 测量项 | 重点观测 |
|---|---|
| TIM13 | 周期、入口迟到、执行最大值、漏周期数 |
| UART5 / USART3 | ISR 最大执行时间、ORE/FE/NE、DMA/环形缓冲覆盖、解析积压 |
| 全局临界区 | 最长关中断区间，与约 23.8 us 的 UART5 字节时间比较 |
| IMU | 实际新采样间隔、超过 20/50 ms 的次数、重对准次数 |
| Mahony | 单次计算平均/最大周期数，单独计入主循环调度等待 |
| I2C/UI | 正常/失败事务用时，开关屏/状态页刷新最长阻塞 |
| RDK | 发帧启动间隔、采样到发帧年龄、帧有效位抖动 |
| 内存 | 最小 MSP、栈高水位和 ISR 最大嵌套 |

CYCCNT 计时若覆盖了被其他 ISR 抢占的区间，得到的是包含抢占的耗时；需保留这个值评估响应，同时用排除嵌套重复计数的方法估算纯 CPU 成本，不能把各层 inclusive 用时直接累加。健康时、开状态页、旋转菜单、ELRS 高频输入、RDK 连续/坏帧输入，以及 I2C/SPI 故障退避场景都要测试。

建议先设验收目标并通过测量调整：IMU 采样间隔正常稳定在目标附近、UI 操作不再触发 50 ms 重对准、持续通信无 ORE/缓冲覆盖、控制 ISR 执行明显小于控制周期且最长值有余量。上述目标尚未在实板验证。

## 推荐实施顺序

1. 增加轻量计时与错误计数，修复 UART5/USART1 接收恢复、USART1 启动窗口及 RDK 时间快照问题。
2. 重做 OLED 分片/变化刷新与外围设备故障退避，保证主循环的最大工作片段受控。
3. UART RX 循环 DMA + 短 ISR + 带接收时间戳的延后解析；RDK TX 改 DMA，统一中断优先级。
4. 将 IMU 采样与关键工作以有预算的协作调度运行，DRDY/FIFO 用于采样保存；里程计后台化时保留每周期采样和实际 dt。
5. 清理重复双精度归一化、降低灯带刷新、按实测控制带宽调整轮速低通和 PID 周期。
6. 补齐故障关断、独立看门狗及栈水位验证。

当前任务规模可以先用有时间预算的协作式调度落地，后续再根据实测的时限和任务复杂度决定是否引入 RTOS。
